## 0. What the system is

Four parts, all in one repo:

| Part | Where | What it does |
|---|---|---|
| Environment | `src/env/**` | Stratego rules as a **batched CUDA simulator**, exposed to Python by pybind11 |
| Policy + value | `pyengine/networks/legacy_rl.py`, `move_transformer.py` | A transformer over the board-state planes; self-play RL |
| Belief model | `pyengine/belief/**`, `pyengine/networks/*belief*.py` | Infers the **types of the opponent's hidden pieces** from the observed trajectory |
| Arrangement model | `pyengine/networks/arrangement_transformer.py`, `pyengine/arrangement/**` | Generates the **setup** (piece placement) that games start from |

On top of those sits a **test-time search** (`pyengine/core/search.py`) that
samples beliefs about the hidden state and searches over them.

The claim we care about ("how could this be general purpose on our GPUs") is
mostly a claim about the **environment**: it is a rules engine whose entire
state for one game is a fixed-size POD struct, and whose entire batch is one
contiguous array of those structs, stepped by one CUDA kernel. Everything else
(policy, belief, arrangement) is ordinary PyTorch that happens to be fast
because the environment is fast.

## 1. The environment, batched on the GPU

### 1.1 The container

`StrategoRolloutBuffer` (`src/env/stratego.h:66`, implementation
`src/env/stratego.cu:42`) owns the whole batch. It is a **circular buffer of
rows**: `buf_size` rows, each row holding `num_envs` independent games. The
current row is `current_step_ % buf_size` (`src/env/stratego.h:412-413`).

State per game is a `StrategoBoard` (`src/env/stratego_board.h`), a plain
struct of:

- `Piece pieces[10][10]` — `Piece` is **exactly 16 bytes** (`static_assert` at
  `src/env/stratego_board.h:80`), holding the piece type (4 bits), colour
  (2), visible (1), has_moved (1), the piece id, and eight 2-byte history
  planes (threatened / evaded / actively-adjacent, protected / protected-against
  / was-protected-by / was-protected-against, two entries each);
- `DeathStatus death_status[2][100]` — 2 bytes each (`src/env/stratego_board.h:107`);
- the last-move bookkeeping (`last_moved_piece_type`, `prev_dst_abs`, `prev_prev_dst_abs`).

Because the struct is fixed-size and POD, `num_envs` games are one contiguous
allocation and a kernel can index game *i* as `d_boards + i`. **This is the
whole trick**: no per-game object, no dispatch, no virtual call. `d_boards_`
holds `buf_size * num_envs` boards and the row stride is `num_envs`
(`src/env/stratego.cu:735-737`).

### 1.2 The tensors handed to the policy

`src/env/stratego.h:70-88`:

| Tensor | Shape | dtype |
|---|---|---|
| `board_state_tensor` | `(num_envs, 355, 10, 10)` | float32 CUDA |
| `infostate_tensor` | `(num_envs, INFOSTATE_CHANNELS, 10, 10)` | float32 CUDA |
| `legal_action_mask` | `(num_envs, 1800)` | bool |
| `reward_pl0` | `(num_envs,)` | float32 CUDA |
| `is_unknown_piece` | `(num_envs, 10, 10)` | bool |
| `piece_type_onehot` | `(num_envs, 10, 10, 14)` | bool |
| `unknown_piece_type_onehot` | `(num_envs, K<=40, 14)` | bool |
| `unknown_piece_has_moved` | `(num_envs, K<=40)` | bool |
| `unknown_piece_position_onehot` | `(num_envs, K<=40, 100)` | bool |
| `move_summary_history_tensor` | `(move_memory, num_envs, 6)` | uint8 |

The 355 board-state planes are documented channel by channel in
`src/env/stratego.h:38-65` and generated by name in
`src/env/boardstate_channels.h` (`our_spy`, `their_spy_prob`, `our_hidden_bool`,
`we_threatened_<type>`, `our_deathstatus_<reason>_<type>`, `our_protected_<type>`,
…). The plane list is the *interface* between the rules engine and the network:
adding a rule means adding a plane, not changing a C++ interface.

The **infostate** tensor is the observation the policy actually sees: it is the
board-state tensor *plus* the last `move_memory` moves, injected as extra
planes (src/dst, hidden-and-types, DeepMind-style "dm" planes —
`src/env/cuda/infostate_kernels.cu:4, 78, 138`). It is the "what did I just see
and what did I just do" encoding that a transformer can attend over.

### 1.3 Actions and the legal-move mask

`NUM_ACTIONS = 1800` (`src/env/stratego.h:36`). An action is
`100 * target + from_cell`, where `from_cell ∈ [0,100)` is the source square in
**the acting player's point of view**, and `target ∈ [0,18)` selects the
destination: `target < 9` means "vertical, land on row `target`", `target >= 9`
means "horizontal, land on column `target - 9`"
(`src/env/cuda/action_kernels.cu:127-147`). Everything is from the acting
player's POV; blue's board is mirrored (`row → 9-row`, `col → 9-col`).

So the action space is not "one action per (piece, destination) pair" but "one
action per (source square, destination *line*)", with the distance resolved by
the rule engine. 1800 = 100 squares × 18 lines. Two things fall out of this:

- the mask is a **fixed-size bitmask**, 1800 bools per game, so the policy
  reads it with one gather;
- the mask kernel can be written with **one thread per (game, square)**:
  `LegalActionsMaskKernel` (`src/env/cuda/action_kernels.cu:5`), 100 threads
  per game, each thread resolving its own piece's reachable lines (a scout
  slides, so the thread walks the row/column) and writing 18 booleans.

This is the pattern worth copying: **the mask is computed where the rules are,
not where the network is**, and it is computed with 100× the parallelism of the
step kernel.

### 1.4 The step kernel

`StrategoRolloutBuffer::ApplyActions` (`src/env/stratego.cu:635`) is the whole
per-turn step. In order:

1. **Legality check** (`src/env/stratego.cu:648-687`): recompute the mask,
   `at::gather_out` the selected actions against it, and abort if any action is
   illegal. This is a *debug* check that runs on every step unless the build
   defines `NDEBUG`.
2. Copy the actions into the circular action history, flip `to_play_`.
3. Copy the row's auxiliary state (twosquare state, chase state, counters)
   forward.
4. **`ApplyActionsKernel`** (`src/env/cuda/action_kernels.cu:107`), launched
   with **one thread per game** (`num_threads = 256`,
   `num_blocks = ceil(num_envs, 256)`, `src/env/stratego.cu:776-777`). One
   thread does the entire move for its game: decode the action into absolute
   coordinates, write the 6-byte move summary, update the "actively adjacent"
   bits of the pieces around the previous destination, resolve the combat
   (attack vs. defend, ties, spy/bomb/marshal order), update the death status
   of both sides, and capture the flag.
   *Per game the work is serial; across games it is embarrassingly parallel.*
   The parallelism of the step is `num_envs`, not `num_envs × cells`.
5. `UpdateTwosquareDeath`, `UpdateChaseState` — the two stateful rules.
6. **Auto-reset**: `ResetTerminatedBoardsKernel`
   (`src/env/cuda/termination_kernels.cu:42`) writes a fresh initial board into
   any game that has already terminated, and `ResetTerminationCountersKernel`
   clears the counter.
7. `UpdateHasLegalMovement_` (`src/env/stratego.cu:1051`) — does *either*
   player still have a legal move? This is what detects a stalemate.
8. `IncrementTerminationCounterKernel` (`src/env/cuda/termination_kernels.cu:141`)
   — increments the per-game counter of steps since termination, and fires the
   battle-timeout / game-length-timeout conditions.
9. `ComputeRewardPl0Kernel` (`src/env/cuda/termination_kernels.cu:173`) — the
   payoff is 0 until the game is over, then ±1 for a flag capture or a wipe-out.

The **termination counter** is a neat trick worth stealing. A game that ends
does not reset immediately: `terminated_since` keeps counting (1, 2, 3, …) and
the buffer is only reset once the *other* player has also had a turn, so both
sides get to observe the terminal state
(`src/env/stratego.h:139-190` documents the three cases). Both players'
policies therefore always see a consistent stream of observations.

### 1.5 What the batch buys

One `apply_actions` call advances `num_envs` games by one ply. The policy
network then runs on `(num_envs, C, 10, 10)` — a batched transformer — and the
loop is: *step the whole batch, evaluate the whole batch, step again*. There is
no per-game Python anywhere in the hot path; the Python wrapper
(`pyengine/core/env.py`) only clones tensors and keeps a stats dict.

## 2. The belief model

### 2.1 The question it answers

In Stratego the opponent's pieces are hidden. The belief model predicts **which
piece type each hidden opponent piece is**, from the observable trajectory.

Inputs (`pyengine/belief/belief.py:210-220`):

- the infostate tensor (planes + move history),
- `unknown_piece_position_onehot` `(K, 100)` — where the unknown pieces are,
- `unknown_piece_type_onehot` `(K, 14)` — the ground truth (training only),
- `unknown_piece_counts` `(12,)` — how many of each opponent piece type are
  *still unaccounted for* (this is the constraint that makes the problem
  solvable at all),
- `unknown_piece_has_moved` `(K,)`.

Outputs: a distribution over piece types for each unknown piece.

Networks: `BeliefTransformer` (`pyengine/networks/belief_transformer.py`),
`TemporalBeliefTransformer`, `LSTMBeliefTransformer`, and the legacy
`ARBelief` (`pyengine/networks/legacy_belief.py`) that the shipped pretrained
checkpoint uses.

### 2.2 How it is trained

`Belief.learn` (`pyengine/belief/belief.py:113`) loops:

1. `update_arrs` (`pyengine/belief/belief.py:270`): sample 1024 arrangements
   from the **arrangement model**, drop the terminal ones, and install them as
   the environment's reset distribution. So the belief model is trained on the
   distribution of setups the arrangement model produces, not on uniform random
   setups.
2. `collect_rollouts` (`pyengine/belief/belief.py:253`): play with the RL
   policy until the buffer holds finished games. The buffer stores, per step,
   the belief inputs and, at the end of a game, the true hidden types.
3. `train` (`pyengine/belief/belief.py:170`): the number of gradient steps per
   iteration is `newly_terminal_games // num_batch_per_train` (default 100) —
   training is proportional to games finished, not to steps taken.
4. The loss (`pyengine/belief/belief.py:231`) is a plain cross-entropy of the
   predicted type against the true type, averaged over the *active* (still
   unknown) pieces.

Two reference beliefs are tracked as diagnostics, not as losses
(`pyengine/belief/uniform.py`):

- `marginalized_uniform_belief` — uniform over the types consistent with the
  remaining counts and the positions;
- `uniform_belief` — uniform over types, conditioned only on the counts and
  the has-moved flags.

`mu_kl` and `u_kl` (`pyengine/belief/belief.py:236-249`) are the KL of the
learned belief to those two references. **This is the measurement that tells
you the model learned anything**: a KL-to-uniform number.

### 2.3 Sampling from the belief

`pyengine/belief/sampling.py:18` — `sampling_loop` is an autoregressive loop
over the unknown pieces: for piece *i*, take the model's logits, mask them with
`create_mask` (`pyengine/belief/masking.py:18`, which enforces the remaining
piece counts and the has-moved constraint), and sample. The result is a
`(n_sample, K, 14)` tensor of **complete worlds** — each sample says exactly
which piece is on which hidden square.

`marginalize` (`pyengine/belief/sampling.py:68`) averages the samples into a
per-piece marginal, which is what the diagnostics report.

## 3. Test-time search over sampled beliefs

`SearchBot` (`pyengine/core/search.py:66`) is the piece that makes this a
*search* system rather than a policy system.

For one decision:

1. **Sample the hidden world.** `_generate_env_state`
   (`pyengine/core/search.py:281`) draws `n_sample` complete assignments of the
   hidden pieces, then calls
   `pystratego.util.assign_opponent_hidden_pieces(env_state, samples)` to
   rebuild a *concrete* board state for each sample. Each sampled world
   becomes one environment in a second, auxiliary rollout buffer
   (`self.auxiliary_env`, `src/env/stratego.cu` — `nonsteppable=True`, sized
   `max_num_moves // N_PLAYER`).
2. **Estimate Q per action.** `estimate_q_values`
   (`pyengine/core/search.py:180`): for `depth/2` plies, roll the auxiliary
   buffer out with the policy network (self-play for the opponent), accumulate
   the TD-λ target at the leaves, and average the leaf values **per root
   action** (`cum.scatter_add_` + `counts`). So Q(a) is the mean value of the
   rollouts that started with action *a*.
3. **Blend the search with the policy.** `compute_search_policy`
   (`pyengine/core/search.py:431`):

   ```
   search_logits = (log π_bp + stepsize·Q + temperature·stepsize·log π_magnet)
                   / (1 + temperature·stepsize)
   ```

   with `π_magnet` a weighted-uniform policy over the legal actions (a
   magnet that keeps the search from starving an action it never sampled).
   The result is a softmax over the legal actions.

The **belief samples are the search's branching factor**: the search does not
plan over "all possible hidden configurations", it plans over *n samples drawn
from a learned posterior*. That is the mechanism that makes belief modelling
worth having — a better posterior means the sampled worlds are more plausible,
so the Q estimates are less biased.

The cost is linear in the number of samples, and each sample is a full
game-rollout in the auxiliary buffer. `SearchBot` requires `env.num_envs >= 100`
(`pyengine/core/search.py:82`).

## 4. The arrangement model

`ArrangementTransformer` (`pyengine/networks/arrangement_transformer.py:31`)
generates the **setup**: where each of the 40 pieces is placed in the 4×10
arrangement area, autoregressively, bottom-to-top and left-to-right.

- Input: the prefix as a one-hot over piece types (`N_PIECE_TYPE = 14`),
  embedded and added to a learned positional embedding.
- Backbone: 4 causal self-attention layers (`SelfAttentionLayer`), then a
  LayerNorm.
- Heads: `policy_out` (14 logits per step), `value_out` (a categorical value
  or a scalar), `ent_out` (a prediction of the *future accumulated entropy* —
  the model is explicitly asked to predict how interesting the game will be).
- **Masking** (`_create_legal_action_mask`, `pyengine/networks/arrangement_transformer.py:127`):
  only piece types with remaining count > 0 are legal; and with
  `force_handedness=True` the flag may only go on the right half, because
  left-right symmetric equilibria would otherwise waste half the samples.

`generate_arrangements` (`pyengine/arrangement/sampling.py:23`) samples the 40
cells in a loop, each step a masked categorical draw, and then **flips half the
arrangements left-right at random** (`randomize=True`), because equilibrium
policies are L-R symmetric and the model only ever saw right-handed ones.

How it is trained is the interesting part: it is **not** trained on a
supervised target. The arrangement buffer scores each arrangement by the
rewards the games it produced (`pyengine/core/rl.py:616` `arr_train`, and
`arr_buffer.add_rewards` in `collect_rollouts`). An arrangement that leads to
good games is a good arrangement. The model learns an **equilibrium over
setups**, and the value head gives the "is this setup good for me" signal
directly.

This is the part that maps most directly onto our own work: a **learned
seeder** for worlds and rooms, scored by what actually happened in them, with a
symmetry-breaking trick (handedness) to halve the sample cost.

## 5. The RL loop

`scripts/train/rl_main.py` builds:

- `Stratego` envs (`pyengine/core/env.py:37`) — train env at `num_envs`, test
  env at `num_envs/2`;
- a policy/value net (`MoveTransformer` or the legacy `TransformerRL`), with a
  **categorical value head** over {-1, 0, 1} (lose/tie/win,
  `pyengine/utils/constants.py`);
- an `ArrangementTransformer` (unless `init_approach=uniform`).

One training iteration (`RL.learn`, `pyengine/core/rl.py:242`):

```
update_arrangements  ->  collect_rollouts  ->  prepare_data  ->  train  ->  arr_train
```

- `collect_rollouts` (`pyengine/core/rl.py:395`) plays until the rollout
  buffer is full (`ready_to_train`), under `torch.no_grad()` and autocast
  bf16.
- `prepare_data` (`pyengine/core/rl.py:460`) computes the GAE/TD-λ targets
  (`CircularBuffer.process_data`, `pyengine/core/buffer.py:194`).
- `train` (`pyengine/core/rl.py:484`) is the PPO-style update.
- `arr_train` (`pyengine/core/rl.py:616`) trains the arrangement model on the
  games just played.

The upstream README's demo line is the reference point for our timing work:

```
python scripts/train/rl_main.py --num_envs 128 --rl.dtype float32 --rl.torch_compile false
```

"Iterations usually take 10–20 seconds on an RTX A6000."

## 6. The three mechanisms worth copying

1. **Fixed-size POD state + one kernel per rule.** A game's entire state is a
   fixed-size struct; the batch is a contiguous array of structs; the step is
   one thread per game. No per-game allocation, no dispatch. This is what makes
   a batch of 4096 games cost the same wall-clock as a batch of 128.
2. **The mask lives in the rules engine.** `legal_action_mask` is 1800 bools
   computed by a 100-thread-per-game kernel. The network never has to know the
   rules to know what is legal.
3. **Belief as a learned posterior over worlds, sampled for search.** The
   belief model does not patch the policy; it produces the *worlds* the search
   rolls out in. The same shape transfers to any task with hidden state.

## 7. What does not transfer directly

- The 355-plane observation is Stratego-specific. The *method* (planes named
  after rules, plus a move-history channel) transfers; the planes do not.
- The action encoding ("source square × destination line") is a consequence of
  Stratego's move rules. Our rule systems have different actions.
- The search's cost model (one rollout per belief sample) is linear in samples
  and needs the auxiliary env; on the Thor, where the GPU is also the CPU's
  memory, the auxiliary env's cost is a real constraint.

The design consequences for our own rule systems are in
[batched-sim.md](../design/batched-sim.md).
